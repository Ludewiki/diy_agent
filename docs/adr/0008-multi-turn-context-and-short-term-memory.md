# ADR 0008：多轮上下文管理与 Session 短期记忆

- 状态：Accepted
- 日期：2026-09-01

## 背景

此前每个 Run 只把当前用户消息发送给 Agent。用户在同一 Session 追问“改得轻松一些”时，模型看不到上一轮的城市、日期、兴趣和已生成行程。直接发送全部历史会让 Token、延迟和费用无限增长，也可能使 Agent 陷入无界 Tool 循环。

## 决策

- Worker 在领取 Run 后、调用模型前，读取当前用户消息之前的同一 Session 历史。
- 当前用户消息始终保留；完整历史采用最近消息数量与 Token 双重窗口，至少保留最近一条历史消息，必要时截断其正文。
- 系统提示、历史、当前消息、Tool 和输出分别占用显式预算，预算由环境变量配置。
- 超出窗口的旧消息使用确定性抽取式摘要压缩，不额外调用 LLM。
- `agent_sessions.summary_through_message_id` 作为摘要游标；只把游标之后、新近被淘汰的前缀并入摘要，避免后续 Run 或重试重复总结。
- 摘要作为低优先级历史上下文发送，明确声明其内容不能覆盖当前系统规则。
- 每个 Run 在 LangChain Callback 边界强制限制 LLM 与 Tool 调用次数；超限不可重试。
- SSE、日志、Span 和 Metric 只记录数量、预算与状态，不记录消息或摘要正文。

## 隐私边界

同一 Session 的历史原文和滚动摘要会发送给配置的 DeepSeek API，以完成多轮回答。该行为必须由产品隐私说明覆盖。当前实现不跨 Session 读取消息，也不把正文写入遥测；用户身份隔离、消息保留期、主动删除和敏感信息脱敏属于后续鉴权阶段。

## 后果

追问可以复用上一轮上下文，长会话占用受控，并可通过 `CONTEXT_PREPARED`、OpenTelemetry 和 Web 页面观察实际组装结果。抽取式摘要可靠且无额外费用，但语义压缩能力弱于模型摘要；替换摘要器前必须增加事实保真、提示注入和成本评测。`tiktoken` 是近似预算器，不能代替供应商返回的实际 Token 用量。
